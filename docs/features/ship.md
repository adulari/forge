# Ship: from a finished session to a merged PR in one action

Ship runs the steps a finished session otherwise needs three prompts for ("commit and push", "open
a PR", "merge when green"), stopping at the first refusal with its reason.

| step | what happens |
|---|---|
| `branch` | refuses a busy session (hosted by the daemon, or a terminal chat the daemon sees as mid-turn through its presence heartbeat), a detached HEAD, and the base branch itself ("create a branch first") before anything is committed |
| `commit` | decides the commit set first (below), stages exactly that, and commits it with a message generated by the same trivial-tier call as the Review dock (`POST /api/git/commit-message`), or the message you pass. Nothing to commit is a skip, not a failure. A failing commit hook stops here and the index is put back as it was |
| `push` | pushes the branch, never forced, through the `open_pr` checks ([open-pr.md](open-pr.md)) |
| `pr` | opens the PR with a generated title and body plus the session's provenance section, or updates the push into an already-open PR |
| `watch` | arms PR Watch in `merge` mode (default method `squash`), which pushes `merged` or `blocked` when it settles |

## What gets committed

Ship never sweeps up the whole tree. The commit set is, in order:

1. **What is already staged.** If anything is in the index it is committed as it is and nothing is
   added; other dirty files are listed as left out.
2. **A worktree session:** everything dirty in its worktree (never `.forge/` state or untracked
   build residue).
3. **A shared-tree session:** only the files the change queue attributes to this session
   ([`GET /api/projects/changes`](../../crates/forge-cli/src/serve_git/changes.rs) rules: its
   recorded `write_file`/`edit_file` edits since the file's last commit). Other sessions' files
   and unattributed changes stay uncommitted and are reported as left out.

It refuses, naming the files, when this session's files cannot be separated from another's (a
file two sessions edited), when a file has unresolved conflicts, and when an untracked file looks
like a secret (`.env*` other than `.example`/`.sample`/`.template`/`.dist`, `*.pem`, `*.key`,
`id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `id_dsa*`). Fix by staging what should ship in the Review
dock, or by moving the file out and shipping again.

Because the commit set is decided up front, the push no longer requires a clean tree: other
sessions' uncommitted files stay where they are.

`POST /api/sessions/{id}/ship` takes `{message?, title?, body?, base?, draft?, method?, preview?}`
and answers 200 with `{ok, preview, plan, steps[], branch, base, commit, pr, watch, refused}`;
`plan` is `{source: index|worktree|session, files: [{path, kind}], left_out: [path]}`. With
`preview: true` the branch checks and the plan run and nothing is staged, committed, pushed or
watched; every surface calls it first and shows the file list before the user confirms. a refusal is `ok: false` plus
`refused: {step, reason}`. Unknown session is 404, a bad `method` 400. It needs the
`workspace-write` scope and, like the other PR routes, a direct connection (the Anywhere bridge
carries no `gh` routes).

## Surfaces

- Phone and desktop: **Ship** in the session menu, **Ship to PR** on the Review dock's Ship row,
  and "Ship current session" in the command palette open one sheet. It first lists the files
  that will be committed (or the reason it cannot), then shows the four rows (committed, pushed,
  PR opened, watching), an optional title field (the generated title is used when empty), and the
  refusal reason on the row that stopped. Ship is disabled until the list is there.
- TUI: `/ship` opens the same card with the file list (Enter ships exactly that set, Enter after a
  refusal re-checks); on the board, `S` on an idle live session fetches the list, asks with it in
  the dialog, then ships and toasts the PR or the reason.
- A turn in progress blocks shipping everywhere: `/ship` typed while a terminal turn runs is refused
  ("ship when the turn finishes"), and the route refuses a stored session whose terminal reports a
  turn running even though the daemon does not host it.
- CLI: `forge ship <session> [--title] [-m] [--base] [--draft] [--method]` prints one line per step
  and exits non-zero at a refusal.

The session must be hosted by the daemon for PR Watch to act; a terminal-chat session is armed but
only watched once it is resumed on the daemon (the `watch` step says so).

## Ship over Anywhere

From a phone that reaches the host through the Anywhere relay (away from the LAN), Ship works
the same as on a direct connection, with one switch the owner has to flip first:

```toml
[anywhere]
allow_ship_over_relay = false   # default; true lets a paired device ship over the relay
```

It is also in `/config` (Anywhere > Ship over Anywhere) and in the app's host settings. The relay
cannot change it: `anywhere.*` is a direct-only config section, so flip it on the host itself or
from a direct connection.

- **Off (default).** The Ship sheet reads "Ship over Anywhere is off on this host: enable it in
  host settings", and the host answers `403 ship_over_relay_off` (naming
  `anywhere.allow_ship_over_relay`) to `POST /api/sessions/{id}/ship` and to arming PR Watch
  (`POST /api/pr/watch`). Nothing is committed, pushed or queued.
- **On.** Ship commits only the session's files, pushes without force, reuses an existing PR and
  arms PR Watch in merge mode, so the PR enters the merge queue. A replayed signed command is
  acknowledged once by the host's command journal and never runs twice.
- **Always on.** The PR list, PR detail and diff, PR status and checks, the PR Watch read, the
  merge queue (a queue row opens the PR in the app) and `done` on a session. A host too old to
  bridge them makes the app say "update the host". Creating, commenting on and merging a PR, and
  GitHub Actions, still need a direct connection; Ship plus the merge queue covers landing a PR.

The trade-off: with the switch on, anything that can sign a command as one of your account's
devices can make the host commit the session's working files, push the branch to its remote and
queue the PR for merge, with you away from the machine. Devices paired over the relay act with the
owner's authority (they are not scoped like a viewer link), so a lost or compromised device can ship
until you revoke it (`forge anywhere devices --revoke`). Leave it off if you do not need to ship
from the road. Direct paired links keep their scopes: Ship and PR Watch writes need
`workspace-write`, so a view-only or prompt-only link gets `403`.
