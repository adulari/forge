# ADR-0021: Desktop client surface and startup evidence

## Status

Retained Tauri client; evidence updated 2026-08-04.

## Evidence update

The retained Tauri client is not represented by the earlier 399 ms startup headline. That value
was measured from the JavaScript instrumentation clock, after native process startup, and was
JS-clock-relative. Seven clean paired 1280×800 launches aligned the native `Instant` captured at
the top of `main()` with the JS snapshot:

- process start → first post-hydration paint: **995 ms median**, **926–1,249 ms range**;
- Tauri builder start: 0.012 ms median;
- builder completion → window available: approximately 268 ms median of the pre-window path;
- process start → window available: 318 ms median;
- window → navigation start: 414 ms process-relative median mark;
- navigation → DOM/content-loaded: 168 ms median in the latest series;
- JS module evaluation through mount and first paint is part of the remaining application path.

The prior 399 ms value remains useful only as a JS-clock-relative measurement and understated
real process-start time by more than half. The earlier 640×480 and 1890×1114 startup values are
also JS-clock-relative. The connected seven-run size sweep had overlapping ranges; raster cost
was not demonstrated. React mount was only 28–52 ms, and first paint preceded the first
`/api/sessions` response at every tested size, so the app already paints before daemon data.

The steady-state connected surface is approximately vsync-clean after the startup stall. The
native pre-window interval is dominated by GTK/WebView construction and is not currently an
application-code target. Plugin registration was sub-millisecond per plugin, and updater network
checking runs from a post-load React effect rather than blocking the builder.

The app bundle remains an application-controlled startup target: the clean export measured a
5,589,476-byte entry bundle, with approximately 585,934 generated bytes attributed to the
`lucide-react-native` barrel. A one-attempt resolver-scoped per-icon rewrite was blocked because
Metro/package exports do not expose `dist/esm/icons/*`; no resolver bypass was retained. The
bundle-size opportunity is recorded, but its startup effect remains unmeasured.

The Linux `WEBKIT_DISABLE_DMABUF_RENDERER=1` workaround is required to avoid the verified wlroots
launch crash. Its possible compositing, frame, and startup cost cannot be A/B tested on this host,
so that cost is unquantified. The AppImage XWayland divergence remains release-blocking and its
figures are not comparable to native Wayland captures.

This entry supplies evidence only. It does not re-argue the native-vs-Tauri choice.
